# Pinky for Android

Pinky has one Android app, named **Pinky**. It does two jobs:

- **Desktop mode.** Pinky on a computer drives the phone over adb, and the app's accessibility service reads the screen for it. This is what Pinky Companion did, and it works as before.
- **On-phone mode.** Pinky runs agent tasks on the phone by itself, with no computer: the person types a task, watches, approves, takes over and stops from the phone.

It grew out of the Android prototype in [standalone-phone.md](standalone-phone.md#prototype-results-android), which follows the architecture recommended there ([Android: one app, the companion grown up](standalone-phone.md#android-one-app-the-companion-grown-up)). This note records the decisions and the state of the work, milestone by milestone.

## Names

| What | Name | Why |
| --- | --- | --- |
| Package | `app.pinky.companion` (release), `app.pinky.companion.dev` (debug) | Kept, so installs update in place and desktop Pinky's install, update and checkup keep working. A package name cannot change without a new app. |
| App and service label | Pinky, Pinky (dev) | In every language. The person sees it under Accessibility, in the launcher and in Android's dialogs. |
| Name in desktop Pinky | Pinky for Android (「Android 版 Pinky」, 「Android 版 Pinky」) | Desktop Pinky's cards, checkup and settings speak of the app on the phone; "Install Pinky" there would read as Pinky installing itself. Steps that name the app in the phone's own settings say Pinky, as the phone does. |
| APK file | `pinky-android.apk` | In the desktop bundle and as a release asset. Was `pinky-companion.apk`. |
| Go package, sockets, environment variables, `assets/pinky-companion.json`, remote temp files | unchanged | Not seen by people. Renaming them would only break running installs and scripts. |

Desktop Pinky recognises the service under both labels (`companion.App.OldLabel`): the phone may still have the old build, labelled Pinky Companion, until desktop Pinky updates it.

The prototype's own app, `app.pinky.standalone` (`android/standalone`), is gone. Its sources live in `android/companion` now, its control and core socket names follow the companion's (`@pinky_core`, `@pinky_core_dev`), and `scripts/standalone.sh` became `scripts/androidcore.sh`.

## Milestone 1: one app, desktop mode unchanged

### What is in which build

`res/values/bools.xml` holds `on_phone_ui`, which decides everything on-phone mode adds. It is true in every build since 2026-11-13 ([below](#release-builds-with-tasks-on-the-phone)); until then it was false in release builds, and the table shows what that meant:

| | Release (ships) | Debug |
| --- | --- | --- |
| Launcher entries | Pinky's debug page only | the debug page and Pinky tasks (`TaskActivity`) |
| Service capabilities | retrieve windows and perform gestures | also `canTakeScreenshot` |
| `gesture` and `global` | served: Pinky on a computer taps through them on Xiaomi phones' background displays (GitHub issue #48) | served |
| `screenshot`, `launch`, `apps` and `on_phone` | `unknown_command` / `unsupported` | served |
| `INTERNET` permission | no | yes (`src/debug/AndroidManifest.xml`) |
| Go core (`libpinkycore.so`, arm64) and its stand-in for `armeabi-v7a` and `x86_64` | yes, since 2026-11-12, unused until `on_phone_ui` turns true ([one APK](#one-apk-for-every-phone)) | yes, built by `scripts/androidcore.sh` |
| Size | about 24 MB with the core (142 KB before) | 24 MB |

So on-phone mode stayed hidden in releases until 2026-11-13. A release build asks Android for what Pinky Companion asked for plus performing gestures, which desktop mode needs on Xiaomi's MIUI and HyperOS: they drop the taps adb sends to a background display, so Pinky on the computer taps, swipes and presses back there through the service instead ([android.md](android.md), GitHub issue #48). Android's consent dialog for the service then also says it can perform gestures, and the service's description says why.

### On-phone mode

On-phone mode is a flag the service keeps in its own preferences (`mode`, `on_phone`):

- Only the app itself turns it on or off, with the `on_phone` command over the companion socket. A connection from another uid (adb, desktop Pinky) gets `forbidden`. Opening the task screen turns it on: the screen finds the core down and asks the service to start it. It turns the mode on again each time the core has the phone again, for a core that outlived the service (below).
- While it is on, the service keeps itself on (the idle watchdog's limit is 0), runs the Go core and draws Pinky's pill and approval card (`Overlays`).
- It survives a restart of the process or the phone. Turning the service off, in Android's settings or by desktop Pinky, turns it off too, as it clears the service's config.
- `ping` reports it (`on_phone`), so desktop Pinky can tell a phone that runs its own tasks.
- The idle watchdog counts only connections from other uids. The core's own connection and Pinky's screens never keep the service on in desktop mode; in on-phone mode it stays on anyway.

The Go core is loaded once per process and cannot be unloaded. Turning on-phone mode off puts the overlays away; the core stays idle until the process ends. So the core outlives the service: turned off and on again, the service has forgotten the mode while the core runs on, and the task screen turns it on again (above). On the Android 17 emulator, while the service is off, Android caches the app's process and freezes it, even with the task screen in front (the screen runs in `:ui`; `dumpsys activity processes` shows `isFrozen=true`). The core's control socket then takes a connection and a command but answers nothing until the service is on again, and `corectl` waits as long.

### Pinky's own screens

`policy.IsPinkyScreen` replaces `policy.StandaloneApp` and `IsStandalone`. It covers `app.pinky.companion` and `app.pinky.companion.dev` (and their clones), and the gateway blocks every action on them for every agent, from a computer or on the phone, whatever the task allows. Before, the gateway blocked only the prototype's package, so this is a change for desktop agents too: they can no longer open Pinky Companion's debug page. Nothing an agent does needs it.

The other two walls stay as the prototype built them: the service refuses gestures on Pinky's windows and overlays (`OwnUI`), and Pinky's views are `accessibilityDataSensitive` and `filterTouchesWhenObscured`.

## Two modes on one phone

Never two agents at once, and the person always sees who is acting. Milestone 1 needs nothing for this: on-phone mode exists only in debug builds. Milestone 2 adds it before on-phone mode ships:

- **A claim per connection.** A new companion command, `claim` (`{"cmd":"claim","by":"computer"|"phone","task":"…"}`), gives the phone to one client and answers `busy` with the holder's `by` and `task` to anyone else. A claim ends with its connection, so a crashed or unplugged client frees the phone by itself.
- **Desktop Pinky** claims when an agent starts working on the phone, on the connection that already holds its event subscription. If the phone is busy, the task does not start, and Pinky shows the phone as busy: "Pinky on the phone is running a task". An older app without `claim` answers `unknown_command`, and desktop Pinky goes on as today.
- **Pinky on the phone** claims when a task starts. If a computer holds the phone, the task screen says so and Start waits; the core refuses `start` too. An older desktop Pinky that does not claim still holds an event subscription while its agent works; the app counts that as a computer's claim.
- **Desktop Pinky leaves the service on** when `ping` says `on_phone`: the person turned it on for Pinky on the phone, and turning it off would also turn on-phone mode off. `Enable` already leaves a service that is on alone, but two backstops in `internal/driver/android/companion.go` force it off: `quietLocked`, for a service an older Pinky left on for good, and `disableLocked` when the service was on before the agent started. Today they spare it only because the core's connection counts as another client (`companionPeers`); Milestone 2 makes both check `on_phone`. Desktop Pinky still turns the service off when it turned it on itself and on-phone mode is off.
- **Who is acting.** On-phone mode's pill shows while either side works: "In use by your computer" while a computer holds the phone, with Stop when it claimed (Stop ends the claim and the computer's agent gets `stopped`) and without for an older desktop Pinky, and the task's own line for a task on the phone. The pill was to say "Pinky on your computer is working", but it cut that line off at its width limit (55% of the screen), and with Stop it spread over 79% of the top of the screen the computer's agent works on; the short line fits in about 64%. In desktop mode alone nothing changes on the phone: Pinky on the computer shows the person what happens.
- **The desktop side, as built (2026-11-12, `internal/driver/android/companion.go`).** The driver subscribes to `claim` events too when `ping` lists `claim`, and claims (`by: computer`, no task name: the driver does not know it) on that subscription at the agent's first call and as the agent starts working (`held`, through `acting` at the top of Observe, Screenshot, Tap, Swipe, Touch, Key, Type, Launch, drags and pinches, on the main display and on background ones). It releases the claim when the agent stops working. While Pinky on the phone holds the phone those calls return `*driver.BusyError` (`errors.Is(err, driver.ErrBusy)`; `By`, `Task`) and do nothing; the app is asked again after 2 s. A `claim` event with `stopped` makes them return `driver.ErrStoppedOnPhone` until the next `AgentWorking(true)`. Calls with no agent working (the person unlocking the phone from the computer) do not claim. `quietLocked` and `disableLocked` leave on a service whose `ping` says `on_phone` (`companionKept`). Pinky's own overlays (the pill, the card) count as covered on the screen the agent reads (`Tree.OverlaysOf`). Tests: `companion_claim_test.go`.
- **The gateway (2026-11-12, `internal/gateway/onphone.go`).** A `*driver.BusyError` from a read, an action or an app change becomes the error `device_busy` for the agent ("Pixel 9 is busy: Pinky on the phone is running a task of its own (“…”), and only one of them uses the phone at a time. Nothing was done. …"; 503 for uploads), and the phone's status line reads "Busy · Pinky on the phone is running a task" (or "… on another computer is using it") until a read goes through again or the task ends; the agent's task stays, so it can try again. `driver.ErrStoppedOnPhone` ends the task as if the person pressed Stop in Pinky (`OutcomeStopped`: the task reads stopped, its approvals go, the session may not take the phone again for a while) and the call answers `stopped`, saying it was stopped on the phone. Desktop Pinky translates the line and the step's "Pinky on the phone was running a task" (`gwStatusBusyPhone`, `gwStatusBusyComputer`, `stepPhoneBusy`). Tests: `onphone_test.go`. Left: the claim lasts as long as the event subscription, so a task idle for a minute (`companionIdle`) gives the phone up until its next call.

## Milestone 2 so far

On-phone mode is still in debug builds only (`on_phone_ui`), and everything below is in them.

### Pinky's screens on the phone

Both run in the `:ui` process, are closed to agents as the debug page is (`policy.IsPinkyScreen`, `OwnUI`, sensitive content), and speak English, Simplified Chinese and Japanese (`res/values*/phone_strings.xml`).

- **The task screen** (`TaskActivity`) takes the person through setup first: turning the service on, with the hint for Android 13+'s restricted settings and a link to App info, then a key and a model. If the core cannot start, it says why (`core_error` in the service's reply to `on_phone`). Then it takes a task, shows it while it runs (its steps, cost and time, what it waits for, Stop) and how it ended, with its steps under Steps and the tasks that ended before it under Activity ([below](#activity-tasks-that-ended)). Start's errors are named by the core's codes (`no_device`, `no_key`, `no_model`, `no_task`, `busy`, `computer`). When the feed offers an update, a card offers it (Download, Later).
- **Settings** (`SettingsActivity`), as desktop Pinky has them in Settings › Ask Pinky and Approvals: the service (Anthropic by default, or OpenAI-compatible), its key, model and address, each kept per service (`TaskSettings`); a task's limits on steps, time and cost (tokens for a model without prices); when Pinky asks (the core's `policy.Preset`, so it changes only while the core runs); the service and App info in Android's settings; the version and Check for updates. A dialog open on it opens again when the screen is made anew (the phone turned, or the theme or language changed), with what was typed in its box; a key's box opens again empty.
- **Keys** (`Secrets`) are encrypted with an AES key that lives in the Android Keystore and never leaves it. Only the ciphertext is in the app's files. It is neither backed up nor moved to a new phone, which would not have the Keystore's key (`res/xml/data_extraction_rules.xml`: for an app that targets Android 12 or later, `allowBackup="false"` stops cloud backups but not a transfer from phone to phone), and nothing logs a key or its length.
- **The look** (`Look`) is desktop Pinky's palette and type, light and dark (`res/values/colors.xml`, `res/values-night`), built in code.
- **Words** (`Words`) puts amounts, times, a task's end and its steps as desktop Pinky words them (`ui/format.go`, `ui/extras.go`): "You denied: open Settings" with the person's mark, "Waiting for you: tap “Pay”", a step stopped while it waited as "Not done: stopped". The gateway's own words (steps, card titles and details, rule names, the phone's line) come from the core in the app's language too: every control command names the screens' language (`locale`, the string `phone_core_locale`, which each `values*` folder sets to its own language), and the core says those words in it through desktop Pinky's own patterns (`internal/gwtext`) beside the English, in `shown` and `asked` on a step, `title_shown`, `detail_shown` and `rule_shown` on a need, and `line_shown` on the device ([below](#the-gateways-words-in-the-apps-language)). `Words` still reads the English to tell what kind of step it is.
- **The pill** reads the task's last step as Activity does, so an answered approval reads "You answered: …", not "Waiting for you". Its line gives way to its button: a long line no longer pushes Stop or Close onto a second line.
- **Updates** (`UpdateCheck`): the task screen checks the feed at most every 12 hours and offers a higher `version_code` whose asset is Pinky's release APK with a `sha256` and a `size`; Download installs it through `UpdateInstall` (below). The check is off in debug builds and in builds without a version, and the feed does not publish the Android asset yet (below).
- **Errors** say in the app's language what failed and what to do ("Couldn't start the task. Try again."; when the core cannot be reached, restart the phone, then reinstall Pinky). What went wrong goes to the log: `PinkyScreens`, or `PinkyOverlays` for the card. A key that could not be saved logs only the exception's class, as its message could say how long the key is.
- **Staying alive** (`Battery`): Android stops or holds back an app whose battery use is optimized, and MIUI and HyperOS, EMUI, ColorOS and Funtouch OS also stop apps that are not allowed to autostart, accessibility services included. Pinky asks the person to lift both and changes nothing itself. Once Pinky is set up, the task screen shows a card, "Keep Pinky running", with Allow, which opens Android's own dialog (`ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`; without it the list of apps' battery optimization, then App info), and on those vendors' phones Open Autostart, which tries the vendor's known autostart pages and falls back to App info. The card stays until the battery is unrestricted and, on those phones, until Later, as whether autostart is on cannot be read. Settings › This phone has a Battery row (Unrestricted or Optimized; tapping it asks, or opens App info once unrestricted) and, on those phones, an Autostart row. The screen stays on during a task anyway: the pill's window keeps it on. The dialog's permission is in the main manifest.

### Two modes: the phone's side

[Two modes on one phone](#two-modes-on-one-phone), as far as the phone goes, through the companion's `claim` ([companion-protocol.md](companion-protocol.md#claim)). Desktop Pinky does not claim yet ([Next](#next)), so for now the phone sees it as an older desktop Pinky.

- **The app** serves `claim` and `claim` events in every build. A release build gains only the command and the feature: nothing on the phone claims there, and without on-phone mode a computer's claim changes nothing on the phone.
- **The core** claims the phone when a task starts and releases it when the task ends (`standalone.Claims`; on Android `local.Claims`, on the core's own subscription to `claim` events). `start` checks the device, the key, the task and the model first, then claims, and answers `computer` while a computer holds the phone. If the service restarts during a task, the core claims again; if a computer took the phone meanwhile, the task stops and reads as stopped, as if the person had pressed Stop.
- **The core's state** has `computer` while a computer holds the phone: its `task`, if it named one, and `stoppable`, false for an older desktop Pinky. `stop` with `computer: true` ends a computer's claim (`corectl stop -computer`).
- **The task screen** shows a card meanwhile: "Pinky on your computer is using this phone", the computer's task, "You can start a task here when it's done", and Stop when the claim can be stopped. Start waits, and a `start` the core refuses says "Pinky on your computer is using this phone. Try again when it's done."
- **The pill** reads "In use by your computer", with Stop, or with no button for an older desktop Pinky. Stop on the pill or on the card ends the claim, and the computer hears `stopped`.

### Activity: tasks that ended

The phone keeps the tasks Pinky did on it for 30 days, as desktop Pinky's Activity keeps a computer's.

- **The task screen** lists under Activity the five latest tasks that ended, leaving out the one whose end it shows, with Show all when there are more. Each row has the task's words (two lines at most), how it ended in a word, when it started and what it used (steps, cost or tokens, time; only how long it took for a task the core kept no record of). The word takes the end card's color: Done green, Stopped grey, the rest amber, so a task that reached a limit reads Stopped in amber. Activity hides while a task runs.
- **Activity** (`HistoryActivity`) lists them all by day (Today, Yesterday, then the date, as desktop Pinky does), 30 at a time with Show more. A row opens **the task** (`PastTaskActivity`): its words in full, its day and time, how it ended as the task screen showed it (the end card without Dismiss) and its steps, or that Activity no longer has it.
- **The core** keeps them. The gateway keeps each task and its steps in its history database in the app's files, as on a computer, and deletes them after 30 days (`Options.KeepDays`). How the core's agent ended a task (its end, summary and usage) is not the gateway's, so the core keeps it beside that database in `runs.json`, one record a task, at most 1000, for as long. A task the app never saw end (it stopped or was updated during the task) reads as failed, and a run that failed before it reached the phone is not there. Outcomes are done, stopped (by the person or a limit), failed, and not started (the API refused the key).
- **The control socket's** `history` lists the tasks that ended, newest first: `limit` of them (20 by default, at most 100) that started before `before` (Unix milliseconds, 0 for now), and `more`. With `id` it answers one task with its steps, or the code `gone`. `corectl history [-before MS] [-limit N]` and `corectl history ID` print them.
- Not yet: choosing how long to keep tasks, clearing them, screenshots of the steps, and running a task again.

### The gateway's words in the app's language

Since 2026-11-13 the pill, the task screen, the approval card, Activity and a past task say the gateway's own words (its steps, a card's title, detail and rule, the phone's line) in the app's language, as desktop Pinky does; before, "Connected to Google …" and "Opened 时钟" stayed English inside a Chinese screen. Only what the person reads changes: what goes to the model, MCP results and logs stay the gateway's English.

- **The words** are desktop Pinky's: its patterns moved from `ui/gwtext.go` to `internal/gwtext` (with the helpers they share: `ruleName`, `joinAnd`, `imperative`, `scopeLine`, `newAgentNeed`, `lowerFirst`), and `ui/gwtext.go` keeps the old names as aliases. The catalogs are `cmd/pinky/locales`, already in the core.
- **The language:** any control command may carry `"locale"` (`en`, `zh-Hans`, `ja`). The app sends the string `phone_core_locale`, which each `res/values*` folder sets to its own language, so the core speaks what the app's strings speak, whether the phone's language or a per-app one (`CoreClient.speak`, before each subscription and each `history`). The core keeps one language for the process, the last one named (`internal/standalone/shown.go`, through `i18n.SetLocaleFunc`).
- **The fields,** beside the English and only when they differ: `shown` (the step's line, and its second line) and `asked` (what a step that waited for the person asked, "点按“Pay”") on a step in the state and in `history`; `title_shown`, `detail_shown` and `rule_shown` on a need; `line_shown` on the device. All additive: an older app reads the English as before. `Words` still reads a step's English `text` for its kind (waiting, a handoff, a question) and shows `shown` and `asked`; `Words.shown` falls back to the English field.
- **Not on the iPhone:** `internal/standalone` is also the iPhone's core, linked into its network extension, which iOS holds to 50 MB ([iphone-app.md](iphone-app.md)). `shown.go` is built for `!ios` only; on `ios`, `shown_ios.go` leaves every `*_shown` field empty and ignores `locale`, so `GOOS=ios` links neither `internal/gwtext` nor the catalogs (`go list -deps ./ios/core ./ios/onphone` lists none of `cmd/pinky/locales`, `mygo/locales`, `internal/gwtext`). ### The wait before the first step

Filmed on 2026-11-13, a task to start a 3-minute timer sat about 7 s on the launcher before Clock opened. It is the model, not Pinky. With a fake model (no thinking, timings logged in milliseconds) on the emulator: from `start` to the first model request under 50 ms, `phone_apps` about 60 ms, `phone_observe` 4 to 44 ms, from the model's answer to Clock's launch intent 80 to 170 ms, and Clock's cold start (`Displayed`) about 640 ms; `phone_launch` returns 1 to 1.3 s after Clock already shows (the settle wait), which does not delay what the person sees. A whole 20-turn fake task took about 0.4 s. In the filmed run (`group/deepseek`) the state showed the first model step done 2.9 to 4.1 s after Start (9,223 tokens) and the second 5.3 to 6.6 s (18,791): the first was a read with no step in history (the pill still said "Connected…"), most likely `phone_apps`, the second `phone_launch`. So the wait is two model round trips of 2.5 to 3 s each; Pinky's own share is 0.1 to 0.2 s, and nothing was changed. Putting the launchable apps in the first message would save one round, at a cost in tokens on every task; it would need measuring with a real model.

### Model services, the check and usage

Since 2026-11-13 Settings offers desktop Pinky's model services ([model-services.md](model-services.md)): the list is `assets/model_services.json`, generated from `internal/pilot` (`ModelServices.kt` reads it), so Settings works while the core is not running.

- **Settings** (`TaskSettings`, SharedPreferences `task`): `service`, and per service `svc_model_<id>` and `svc_url_<id>` (empty while the address is the preset's own). Settings of before there were services map to one as on the computer (`serviceFor`, `modelIn`, `urlIn`): `provider` with `base_url_<api>` and `model_<api>`. Keys stay in `Secrets` under `key_<name>`, the name being `pilot.KeyName` (the service's ID, or `anthropic` / `openai` for the custom entries), so keys saved before need no migration. Ollama and LM Studio need no key; their address on a phone is the computer's on the network.
- **The model row** lists the preset's suggested models, the one typed if it is another, and Other…; local servers and custom addresses take a typed name.
- **The check:** saving a key, a model or an address, or Check now, sends the core `{"cmd":"check", key, service, provider, base_url, model}`; the core checks the model with one tiny request (`pilot.Check`), counts its tokens and keeps no copy of the key. Settings says how it went in the app's language (`phone_check_*`), with the service's own words under it.
- **Usage:** the core counts every request (`model-usage.json` in its data directory); the control socket's `usage` (`since`, a day) lists it by day, service and model. Settings shows today, the last 7 and 30 days and the last 7 days row by row; the task screen shows today's under the limits.
- **corectl:** `model -service S`, `check [-key K] [-service S …]` (the key is a flag, `fake` by default: for `fakemodel` only; a real key is checked from Settings) and `usage [-since DAY]`. `debug_model` takes `service`, or derives it from `provider` and `base_url`.
- **Tests:** `ModelServicesTest` (JVM, `org.json` as a test dependency): the generated file parses, unknown APIs are left out, settings of before map as on the computer, usage parses and adds up.
- **Checked:** the unit tests and the debug build (`scripts/androidcore.sh`); the check and usage through the control socket in `internal/standalone/check_test.go`. Not checked: the screens on an emulator or a phone, and a real model.

### Quick entries: the floating button, Share to Pinky and the tiles

Since 2026-11-13, after Mika's pill (github.com/wangzan101/Mika, its docs only), Pinky's own agent can be reached from any app. All of it is apart from `Overlays` (the pill and the card), so the background display's floating window can grow there without meeting it.

- **The floating button** (`QuickEntry`, drawn by the accessibility service in on-phone mode): off until the person turns it on in Settings › This phone or with its tile. A tap opens Pinky; a double tap opens the ask panel for "Ask about this screen"; a long press opens it with Android's speech recognizer at once; a drag moves it, and it keeps to the nearer edge. It hides while a task runs, while a computer holds the phone, while the core or the phone is not ready, and over Pinky's own screens. Its window carries Pinky's title, its view is sensitive, and its rect goes to `OwnUI`, so agents can neither see nor press it. The on/off state is a file (`filesDir/floating_button`) and a package-only broadcast, since the UI (`:ui`) and the service live in different processes, whose SharedPreferences caches do not see each other.
- **The ask panel** (`AskActivity`): a card over the app with a box for the question, a mic, and Ask. It says why a task cannot start (no key, no model, the phone not ready, a task running, a computer using the phone) and offers Open Pinky. For a screen it finishes first and the core is called 400 ms later (no window animation), so the task's first read is the app's screen and not Pinky's, which the gateway refuses to read. The screen goes to the person's own model only, through the gateway like any read: blocked apps, hidden codes and the rules apply. The core's `start` takes `screen: true`; `pilot.Extra` adds a line asking the model to answer about the current screen.
- **Share to Pinky** (the `ShareToPinky` alias of `AskActivity`, for `SEND` text and pictures and `SEND_MULTIPLE` pictures): text and links go as `shared` (at most 20,000 characters), pictures as `images` (at most 4, each scaled to 1568 px on its longer side and sent as JPEG at quality 85). The model gets the pictures before the task's text (Anthropic image blocks, OpenAI `image_url` parts). With an empty box, the task is "Tell me about what I shared."
- **With the background screen** (android-wadb.md): the floating button hides whenever a task runs, so it never shows beside the background screen's floating window (`AgentWindow`), which shows only while a task runs there; the person stops or steers that task from its window and the pill, and starts the next one once it ends. Both are accessibility overlays on the phone's own display, titled as Pinky's, sensitive, and listed in `OwnUI` (the button through `setBubble`, the window through `Overlays`); the background display holds neither, and `OwnUI.check` refuses touches on them there as everywhere. A question about the screen connects with `own_screen` (`pilot.Extra.Screen`), so it reads the app the person looks at and not the empty background display; the gateway's rule for `own_screen` stands (a phone the person used in the last minute during a background task starts paused until they hand it over).
- **Continue** keeps what was shared: the screen, the text and the pictures are in the conversation's first message, which a continued task sends again (`TestStartWith`).
- **Quick Settings tiles** (`QuickTiles.kt`): New task (the panel with the task box alone, after unlocking) and Floating button (on or off).
- **Voice input** in the task box and the panel: `RecognizerIntent`, Android's own recognizer, so Pinky needs no microphone permission. The manifest's `<queries>` names the action, for Android 11 and later.
- **Checked** on an Android 17 emulator (debug build, a fake Messages API that logs each task's first message): the button hidden over Pinky's screens and shown over Settings, the launcher, Files and the share sheet; a double tap, Ask, and a first message carrying Settings' screen (not the panel, and without the button); a tap opening Pinky; a long press opening the panel and Google's speech recognizer (cancelled: the emulator has no microphone, so a recognized result was not tried); a picture shared from Files reaching the model as an image block before the text, and text and a link from `am start`; both tiles through `cmd statusbar`; the Settings row; the panel in Chinese.
- **Not done:** the button can sit over the keyboard (over its mic key) and could move clear of the IME. The pill's Done line cuts a long answer short; the whole answer is on Pinky's end card, and a card over the app for answers would suit "ask about this screen" better.

#### One APK for every phone

The owner chose one APK (2026-11-12) over two by ABI or the core as a download of its own. Release and debug builds carry `build/go/jniLibs` (`sourceSets.main`), which `scripts/androidcore.sh core` fills: Pinky's core for arm64 (`lib/arm64-v8a/libpinkycore.so`, 21.2 MB, stored uncompressed so that Android maps it straight from the APK) and, for `armeabi-v7a` and `x86_64`, `libpinkystub.so`, an empty library of 1 to 2 KB. Android installs an APK with native code only on a phone that runs one of its ABIs (`INSTALL_FAILED_NO_MATCHING_ABIS`), and picks the phone's best ABI the APK has: arm64 phones get the core, 32-bit-only phones (some Android Go phones) and x86_64 emulators the stand-in, under another name so that the core does not load there; they work with a computer as before. `aapt2 dump badging` reads `native-code: 'arm64-v8a' 'armeabi-v7a' 'x86_64'`. Desktop Pinky installs the same APK on every phone, so `install.go` and `companion_update.go` did not change.

- **Builds:** `make companion-release` builds the core first, so a release needs the Android NDK: GitHub's Ubuntu runner has it preinstalled (`ANDROID_NDK_HOME`; not yet tried in a release run), and Android Studio's SDK Manager installs it on a Mac. `scripts/dist.sh companion` stops when a release APK lacks any of the three libraries, and warns for a development build. `make companion` (the debug build) carries whatever `build/go/jniLibs` holds.
- **Size:** the debug APK is 24.2 MB with the core, and every desktop package carries the release APK. Compressed, the core is 7.8 MB (`gzip -9`); `useLegacyPackaging = true` would make the download about 13 MB smaller, but Android would extract the library on install, so it would take space twice on the phone.
- **The feed:** `release manifest` adds `pinky-android.apk` as `android-arm64`, with the `version_code` the build wrote into `assets/pinky-companion.json`, the key Pinky for Android reads (`UpdateCheck.ASSET`; `TestFeedPinkyForAndroidReads` keeps the two the same). One APK serves every ABI under that key. A release without the APK has no manifest; a dry run's leaves it out. The release workflow's Publish job takes it from the Companion APK job, and `scripts/release.sh` puts it in `dist/<version>/`.

## Building and testing

- `make check` builds and tests the Go side, the companion included.
- `android/companion/gradlew -p android/companion assembleRelease` builds the release APK (signed when `PINKY_COMPANION_KEYSTORE` is set).
- `scripts/androidcore.sh` builds the core for arm64 with the NDK and then the debug APK; `scripts/androidcore.sh core` builds only the core.
- `cmd/corectl` drives the core's control socket from adb as the app's uid (`run-as app.pinky.companion.dev`); `cmd/fakemodel` stands in for the model (`-pinky "Pinky (dev)"` for the debug build's label); `cmd/localbench -dev` times the debug build's commands.
- `corectl model [-service S | -provider openai|anthropic] [-base-url U] [-model M]` sets a real model in a debug build as Settings does, and saves the key it reads as one line from standard input, so that the key stays off command lines: pipe it in from a script that reads it (`… | adb shell run-as app.pinky.companion.dev ./corectl model …`), and never type it into a shell. It goes over the service's socket as `debug_model`, which only debug builds answer, and only for the app's own uid; neither side logs the key. Then start tasks from the task screen: it hands the saved key to the core, `corectl start` does not.
- `uiautomator dump` makes Android unbind Pinky's accessibility service and bind it again, which restarts its socket; prefer `companionctl tree` or a screenshot while a test watches claims or a task.
- Device tests: `scripts/devlock.sh <id> env PINKY_DEVICE=<serial> go test -tags device …`, following the phone rules in [WORKING.md](../WORKING.md).
- `adb shell cmd locale set-app-locales app.pinky.companion.dev --locales zh-Hans` (or `ja`) shows Pinky's screens in another language without changing the phone's; the same command without `--locales` goes back.
