# Platform notes (round three)

The platform session's work in round three: PINs in the system keychain on macOS, Windows and Linux; FFmpeg inside Pinky.app; the companion APK in the `.dmg`; CI on Linux, Windows and macOS. Branch `claude/platform-5568b2`.

## Secrets (`internal/secret`)

`secret.System()` returns the system's store; the `Store` interface did not change. Every store keeps a secret under the service `app.pinky.desktop` (`secret.Service`) and the account (`secret.PINAccount(deviceID)` is `pin:<device id>`), and `Reveal` asks the person before it reads anything. `Reveal` returns `ErrNotFound` before any prompt when nothing is saved, `ErrCancelled` when the person cancels or fails, `ctx.Err()` when the context ends first, and an error wrapping `ErrUnsupported` when the system cannot ask anyone. It blocks until the person answers, so callers run it off the UI thread.

### macOS: the login keychain and LocalAuthentication

- Items are generic passwords (`kSecClassGenericPassword`) of the login keychain, written with `SecItemAdd`/`SecItemUpdate`, found and read with `SecItemCopyMatching`, removed with `SecItemDelete`, all through purego (`keychain_darwin.go`). The dictionaries are CoreFoundation objects; nothing goes through cgo.
- `Reveal` first checks that the item exists, then asks with LocalAuthentication: an `LAContext` evaluates `LAPolicyDeviceOwnerAuthentication` (Touch ID, an Apple Watch, or the Mac's password) with the reason, through purego's Objective-C runtime and a block for the reply (`presence_darwin.go`). The system's sentence reads "Pinky is trying to <reason>", so the reason is a verb phrase such as "unlock Mi 10 Pro". Cancel, failure, fallback and system or app cancel map to `ErrCancelled`; a context that ends calls `-invalidate`, which takes the prompt away; no password on the Mac and no window session (`LAErrorNotInteractive`) wrap `ErrUnsupported`.
- **Decision: the app gates reads itself.** The data protection keychain, where an item could carry a biometry access control (`SecAccessControlCreateWithFlags` with `.userPresence`), needs a `keychain-access-groups` entitlement and a real signing identity; Pinky.app is signed ad hoc, which gets `errSecMissingEntitlement`. So the item lives in the file-based login keychain and Pinky asks with LocalAuthentication before it reads. What protects the PIN from other programs is the item's access list, which trusts the program that created it: anything else gets macOS's own "wants to use your confidential information" prompt. A consequence: each rebuild of an ad-hoc signed Pinky is another program to the keychain, so its first read of a saved PIN shows that prompt too ("Always Allow" ends it for that build). A Developer ID signature makes builds the same program.
- `Has` adds `kSecUseAuthenticationUIFail`, so it never asks anything: a locked keychain reads as nothing saved.
- The item's label is "Pinky (pin:<id>)", which is what Keychain Access lists.

### Windows: the Credential Manager and Windows Hello

- Items are generic credentials (`CredWriteW`, `CredReadW`, `CredDeleteW` through syscall) with the target `app.pinky.desktop/<account>` (as keytar and MyGo name theirs) and `CRED_PERSIST_LOCAL_MACHINE`, so a phone's PIN does not roam with a domain profile. Windows encrypts them for the user. Copies of the secret are wiped before they are freed.
- `Reveal` asks through Windows Hello when it is set up (`presence_windows.go`): the WinRT class `Windows.Security.Credentials.UI.UserConsentVerifier`, reached with `RoGetActivationFactory` and its COM vtables. `CheckAvailabilityAsync` first; then `IUserConsentVerifierInterop::RequestVerificationForWindowAsync` owned by Pinky's window when one is in front (Windows 11), else `RequestVerificationAsync`. Async operations are waited on by polling `IAsyncInfo`; a context that ends calls `Cancel`. The interface IDs come from the SDK's headers (MinGW's IDL, win32metadata); the one of `IAsyncOperation<UserConsentVerificationResult>` is derived from its WinRT signature, which `TestAsyncOperationIID` recomputes.
- Without Hello (not set up, not allowed, or refused to a program without a window), it asks for the signed-in account's password in `CredUIPromptForWindowsCredentials` (`CREDUIWIN_ENUMERATE_CURRENT_USER`) and checks it with `LogonUserW`, three tries, as Chrome did. That dialog cannot be taken away early: when the context ends while it shows, the answer is dropped once the person closes it.
- `ERROR_LOGON_FAILURE` is a wrong password (the dialog asks again); any other failure is an error, with one exception for accounts without a password (issue #41, below). `passwordVerdict` (`password.go`, no build tag, so its table test runs on every system) makes that decision. A Microsoft account that submits nothing, or only wrong passwords, gets `ErrMicrosoftAccount`, whose message asks for the Microsoft account's password: people who sign in with a PIN or Hello may not know the account has one. The account is a Microsoft account when its local account is connected to one (`NetUserGetInfo` level 24), its token has a group in `S-1-11` (the Microsoft account's own SID), or the dialog's domain is `MicrosoftAccount`.
- Each check logs one line to the app's log (`secret.SetLogger`), "confirm with the password", with the step that decided and the values behind it: the dialog's name and domain, as unpacked and as parsed, `LogonUserW`'s code, whether the name resolves to the signed-in account, that account (`DOMAIN\name` from its token), whether and how it was found local, its account domain, this computer's names, whether it is a Microsoft account and how that was found, any lookup that failed, and the second `LogonUserW`'s code. Never the password. The Windows Hello outcome is logged too. Diagnostics replace the user name with `<user>` and take out e-mail addresses.

### Windows: accounts without a password

Windows' default policy "Accounts: Limit local account use of blank passwords to console logon only" (`HKLM\SYSTEM\CurrentControlSet\Control\Lsa\LimitBlankPasswordUse`=1) refuses a local account with a blank password any logon `LogonUserW` makes, network or interactive, with `ERROR_ACCOUNT_RESTRICTION` (1327). So a person whose account has no password could never confirm (issue #41).

An empty password now counts as right when the account Pinky runs as has no password, whatever name the dialog returned. That account comes from the thread's token (its SID, then `LookupAccountSid`). It must be an account of this computer: its SID is the local account domain's SID (`NetUserModalsGet` level 2) plus one part, or, when that cannot be read, its domain is one of this computer's NetBIOS or DNS names (`GetComputerNameEx`, ignoring case). Then `LogonUserW` for its own name in the local account database (domain `.`) with an empty password must sign in (policy off) or answer 1327. The dialog's name only decides whether to ask: after a 1327, or after a 1326 for a name that names another account or none (a display name, a UPN). A 1326 for the signed-in account's own name is a wrong password without a second try: the name resolves (`LookupAccountName`) to its SID, or does not resolve and its user part is its name (an unknown domain, such as a computer name Windows does not look up). The second try is a failed sign-in for an account with a password, and Windows locks an account out after 10 failed sign-ins in 10 minutes by default (the tests locked the runner's account out once, below), so a person who has a password and submits an empty one makes one failed sign-in for any form of their own name, and two only for a name Windows cannot tie to the account. `.\user`, which `CredUIParseUserNameW` does not parse, signs in against the local account database (domain `.`). Domain accounts and accounts Windows cannot name never pass with an empty password; a 1327 for a password that is not empty stays an error.

The first fix (2026.1110.2) asked only when the dialog's domain was empty, `.` or the computer's NetBIOS name (`windows.ComputerName`), and then looked up `<NetBIOS name>\<user>`. Kutius, who reported #41, still could not confirm with it. The likely cause: the dialog named the account with another domain (the DNS host name, a computer name longer than NetBIOS's 15 characters, which Windows cuts, or another spelling), which `LogonUserW` on a workgroup computer still maps to the local account and answers with 1327, while the old check gave up on that domain with the same error as before the fix. Not confirmed with the reporter's own diagnostics, which the new log line will show. The CI runs below reproduce it with an unknown domain, and show that the first fix also took `.\user`, the full name and `user@computer` for wrong passwords.

This is safe because Windows answers 1327 only after the blank password has matched. #### The third fix: the dialog's password comes protected (2026-11-10)

Kutius's diagnostics from 2026.1110.12 showed `empty=false` and 1327 for the dialog's own `IZUKI\<user>`, on a local account found local by its account domain: the empty password did not count as empty, so the blank-password path never ran. The cause: `CredUIPromptForWindowsCredentials` may hand back the password protected with `CredProtect`, a string starting `@@D`, and `CredUnPackAuthenticationBufferW` with flags 0 unpacks it as it is. On the runner (run 42775282099), an empty password protected by `CredProtectW` or packed with `CRED_PACK_PROTECTED_CREDENTIALS` unpacks as 36 characters (`@@D…`, `CredIsProtectedW` type 1, `CredUserProtection`); `LogonUserW` reads protected passwords itself: for the blank-password account a protected empty password got 1327 and a protected `x` 1326, and for an account with a password its protected password signed in. That is why accounts with a password always worked, why a blank one got 1327 although "something" was typed, and why the earlier CI runs, which packed plain buffers, passed. A plain non-empty password for a blank-password account is 1326, never 1327, so the log line can only be a protected empty password.

`checkPassword` now asks `CredIsProtectedW` about the unpacked password and, when it is protected, replaces it with `CredUnprotectW`'s answer (as the process, then as the thread) before anything reads it; the copy is wiped. The log line gains `protected` ("no", "type N", or "unknown: …" when Windows cannot tell, which counts as plain). A 1327 for a password that is not empty also asks the blank-password question, for the log only (`blank_logon`). Any 1327 that ends in an error wraps `secret.ErrAccountRestricted`, which the UI shows as `unlockErrAccountRestricted`: Windows would not check the password, most likely because the account has none; set a password or a Windows Hello PIN in Windows Settings › Accounts › Sign-in options.

Tests: `TestUnprotect` (Windows, no sign-in) protects "", "x" and a longer password and reads each back, leaves plain strings alone, and unpacks a protected empty password; `check` in `TestBlankPasswordAccount` now runs every case with the buffer packed plain and packed protected and requires the same answer, asserts that `LogonUserW` gives 1327 for the blank account's protected empty password, and creates `pinkypw` with a password to check that its password passes both ways. The runner's own checks use protected buffers only, so they still make 4 failed sign-ins.

Not checked: the real dialog with a person (CI has no one to type); that it protects is inferred from the log above, which nothing else explains.

### Linux: the Secret Service

- Secrets go in the Secret Service (GNOME Keyring, KWallet, KeePassXC) over D-Bus with `github.com/godbus/dbus/v5` (pure Go, BSD; it was already in the module graph). Items have the attributes `service` and `account`.
- **Decision: a keyring of Pinky's own, kept locked.** The Secret Service hands out the items of an unlocked keyring to any program of the user without asking, and Pinky must not lock the person's login keyring. So the items live in a keyring labelled "Pinky" that Pinky locks after every use; `Reveal` locks it (in case something left it open) and unlocks it, and unlocking asks for that keyring's password in the keyring's own prompt. The first `Save` creates the keyring, which asks the person to choose the password; `Save`, and `Delete` on some keyrings, ask to unlock it.
- Limits: the check is as strong as the person's keyring settings (a keyring with an empty password, or set to unlock at login, opens without asking); the prompt shows the keyring's text, not Reveal's reason; secrets cross the session bus in a "plain" session, which only the user's programs reach. No session bus or no Secret Service is `ErrUnsupported`.

## FFmpeg inside Pinky.app

- `make ffmpeg` (`scripts/ffmpeg.sh`) downloads FFmpeg 9.0.2's source from ffmpeg.org, checks its SHA-256, and builds shared libraries into `build/ffmpeg`: `--disable-everything --disable-autodetect`, then the H.264 and HEVC decoders and parsers, VideoToolbox and its hwaccels, the MP4/MOV muxer and demuxer and the raw H.264/HEVC ones, the file protocol, and the `h264_mp4toannexb`, `hevc_mp4toannexb`, `extract_extradata`, `h264_metadata` and `hevc_metadata` bitstream filters; no avdevice, avfilter or swresample; nothing GPL or nonfree ("License: LGPL version 2.1 or later"). `--install-name-dir=@rpath`, `-mmacosx-version-min=12.0` (see [the oldest macOS](#the-oldest-macos)) and header padding for `install_name_tool`. It configures with the fixed prefix `/opt/pinky-ffmpeg` and installs through a staging folder, because the libraries record their configure line (`avutil_configuration()`): no path of the building machine ends up in the app. It took 41 s on the M4 Pro; the four libraries are 5.5 MB (avcodec 2.8, swscale 1.2, avformat 0.7, avutil 0.7) and need only system frameworks (VideoToolbox, CoreMedia, CoreVideo, CoreFoundation, CoreServices).
- libavformat is there for recordings remuxed without re-encoding (decision 8), in case the recorder uses FFmpeg; `video.LibraryDirs()` gives the folders to load it from, in `internal/video`'s order.
- The Windows build (`scripts/ffmpeg.sh build/ffmpeg windows-amd64`) also links Cisco's OpenH264 2.7.0 in as FFmpeg's H.264 encoder, which `internal/driver/ios` uses first because it gives each picture back as soon as it is encoded (Media Foundation's `h264_mf`, which holds a dozen pictures back, stays as the fallback). Its source comes from Cisco's release on GitHub, is checked against its SHA-256 like FFmpeg's, and is built in the same container with Ubuntu 24.04's mingw-w64, as a static library under `/opt/pinky-openh264` — a prefix only that build has; FFmpeg finds it through pkg-config, and its C++ runtime goes in statically with it, so the DLLs import nothing they did not before (`avcodec-63.dll` grows from 4.1 MB to 4.8 MB). `FFmpeg-BUILD.txt` names its version, source and checksum.
- On patents: OpenH264's source is BSD-2-Clause, but Cisco's royalty-free AVC patent licence goes with the binaries Cisco publishes, not with a build linked into Pinky's FFmpeg. Shipping an H.264 *encoder* to other people to use outside the United States (and in the other countries where AVC patents are licensed) is a decision the maintainer owns; nothing in either licence makes it for them.
- `make app` builds them the first time, then `scripts/macapp.sh` copies them into `Pinky.app/Contents/Frameworks` as `libavutil.61.dylib`, `libavcodec.63.dylib`, `libswscale.10.dylib` and `libavformat.63.dylib`, with `@rpath/<name>` install names and an `@loader_path` rpath (they find one another in Frameworks whoever loads them), checks that they need nothing outside the system, adds `FFmpeg-COPYING.LGPLv2.1` and `FFmpeg-BUILD.txt` (version, source, checksum, configure flags) to `Contents/Resources`, and signs the libraries and the app again with the identity `mygo build` used (`MACOS_SIGN`: `macos.signingIdentity` from `mygo.json`, else ad hoc; a Developer ID gets the hardened runtime and a timestamp, and the rebuilt `.dmg` is signed too).
- `internal/video` now looks in `PINKY_FFMPEG_DIR`, then the bundle's `Frameworks`, then the executable's folder, then Homebrew and the system (the executable's path is resolved through symlinks first).
- Loading fixes found on Linux and Windows: a library loaded by its full path looks for its dependencies on the loader's path, not in its folder, so BtbN's libavcodec (which links libswresample) failed from `PINKY_FFMPEG_DIR`; Pinky now loads libswresample from libavutil's folder first, and on Windows loads DLLs with `LOAD_WITH_ALTERED_SEARCH_PATH`. BtbN's Linux builds load libva lazily and abort the whole process when it is missing, so the decoder asks for VA-API only where `libva.so.2` and `libva-drm.so.2` load (`hwLibrariesLoad`, one line in `decoder.go`).

## The oldest macOS

- Pinky needs macOS 13 (Ventura) or later. Go 1.27's linker gives every Mac binary it builds the minimum 13.0 (`minos` in `LC_BUILD_VERSION`), and macOS starts no binary on an older system, whatever Info.plist says. Earlier releases said 12 (`macos.minimumSystemVersion` in `cmd/pinky/mygo.json`, which becomes Info.plist's `LSMinimumSystemVersion`; the cask's `depends_on macos: :monterey`; the READMEs), so a Mac on macOS 12 could download it and install it with Homebrew, and then could not open it.
- Now they all say 13: both `mygo.json` files, the cask (`depends_on macos: :ventura`, which means Ventura or later) and the READMEs. Two checks keep them with the toolchain: `TestMacOSMinimum` (`scripts/release`) builds a small program for darwin/arm64 and darwin/amd64 on any system and fails when its minimum differs from `mygo.json`'s or from the cask's macOS; `scripts/macapp.sh` (make app, and the release) fails when the packaged executable's minimum differs from Info.plist's, or when an FFmpeg library or adb needs a newer macOS than Info.plist names. A Go upgrade that raises the minimum fails CI and the release instead of shipping an app that says it runs where it does not.
- FFmpeg's libraries and adb stay built for macOS 12 (`-mmacosx-version-min=12.0` in `scripts/ffmpeg.sh`, `CMAKE_OSX_DEPLOYMENT_TARGET=12.0` in `scripts/adb.sh`, whose comments still say the app runs on 12). A library built for 12 runs on 13. The release workflow caches both builds by the hash of these scripts (release-cache.yml makes the caches on main), so changing either one, even a comment, builds them again and makes the next release ship new FFmpeg and adb binaries for no gain; change the minimum there with the next real change to those builds.

## The companion in the `.dmg`

`mygo build` signs the app and makes the `.dmg` in one step, so the APK copied into the app afterwards never reached the `.dmg`. Now `make app` stages the APK as `cmd/pinky/resources/pinky-android.apk` (MyGo's resources folder) before `mygo build`, so MyGo copies it into `Contents/Resources` (next to the executable on Windows and Linux, where `FindCompanionAPK` also looks) before it signs, and removes the staged copy afterwards. `COMPANION_APK=path` picks another APK. Since the Frameworks are added after `mygo build`, `scripts/macapp.sh` makes the `.dmg` again from the finished app, reusing the Finder window (`.DS_Store`) and volume icon of MyGo's image, the same `hdiutil` steps, and LZMA compression (`diskutil image create from --format ULMO`, which macOS 27 asks for). Checked by mounting it: the app inside has the APK and the four libraries and verifies.

**Decision:** the libraries go in `Contents/Frameworks`, as Apple lays bundles out, rather than in MyGo's resources (`Contents/Resources`), which would have spared the `.dmg` rebuild. Notarizing (not set up) would have to happen on the final `.dmg`: `make app` passes `-skip-notarize` to MyGo, whose image is replaced.

## CI

`.github/workflows/ci.yml` runs on pushes to `main` and `claude/platform-*`, on pull requests and by hand, with one run per ref at a time (`cancel-in-progress`):

- Linux (ubuntu-latest, Ubuntu 26.04 today) and Windows (windows-latest, Windows Server 2025): FFmpeg 9 from FFmpeg-Builds' (formerly BtbN's) shared GPL builds, kept in the Actions cache and fetched through GitHub's API (`gh release download`) only when the cache has none (their ffmpeg command has x264 and x265 for the test streams; nothing of them ships), build, vet, test with `CGO_ENABLED=0`, and the decoder and keyring tests again with `-v` so the log shows what they did.
- macOS (macos-latest): build and vet only.
- All three: `scripts/smoke.sh`, which builds pinky and `scripts/mcpcall`, starts `pinky daemon --fake` in a private `PINKY_HOME`, checks `pinky devices` lists both fake phones, and drives connect, launch Calculator, observe and release through `pinky mcp`.
- Linux: `go tool mygo build` for Linux and Windows (checks the packaging), then the e2e build of the app under Xvfb (with a session bus from `dbus-launch`); `scripts/uicapture` waits for its window through MyGo's automation socket, checks that it shows "Pixel 9 (fake)", and captures it. MyGo draws it without a GPU. The captures and logs are kept for a week as artifacts.

Results (runs 42324128635, 42325087386 and 42325809410 on the branch): all three systems pass build, vet, the tests and the smoke run, and the Linux runner packages Linux (`.deb`, `.tar.gz`, PKGBUILD) and Windows (`Pinky.exe`) with MyGo (about 2 minutes, in parallel with the Windows job). Linux and Windows decode the H.264 and HEVC test streams in software (the runners have no VA-API or D3D11 video decoder); the window under Xvfb shows both fake phones and is captured at 1280×820. A run takes under 5 minutes, the Windows job's length: macOS 51 s, Linux 2 min 49 s (tests 36 s, window 18 s), Windows 4 min 43 s (building 2 min, tests 64 s, setting up Go 31 s, FFmpeg 3 s). Windows minutes count double and macOS minutes ten times on a private repository.

What CI found and what was fixed (platform-only, small):

- `cmd/pinky/e2e_test.go` did not compile on Windows (`syscall.Kill`); it stops daemons with SIGTERM and checks Unix file modes throughout, so it builds on Unix only now (`//go:build !windows`), and the smoke run covers Windows.
- `internal/api` tests used `/tmp` and Unix paths; `internal/policy` tests checked 0600 modes, which Windows does not have.
- The FFmpeg loading problems above (libswresample, libva).
